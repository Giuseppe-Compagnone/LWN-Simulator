# Devices

A device represents a LoRa or LoRaWAN end device participating in the simulation. Its
configuration is divided into identity, activation, radio receive windows,
location, frame handling, payload generation, and advanced radio behavior.

## Identity and state

| Field | Meaning | User-visible rules |
| --- | --- | --- |
| `id` | Internal unique identifier. | Generated by the server; read-only. |
| `active` | Whether the device is enabled for use. | New devices are active by default. It can be changed while editing. |
| `name` | Friendly name shown in lists, details, and map tooltips. | Required. |
| `devEUI` | Globally unique identifier of the end device. | Required hexadecimal value with exactly 16 characters. It can be generated automatically during creation and cannot be changed during editing. |
| `class` | LoRaWAN device class. | `class-a`, `class-b`, or `class-c`. |
| `activation` | How the device obtains its session parameters. | `oota` (OTAA) or `abp`. The activation choice is fixed after creation. |

The interface displays enum values in a readable form. For example,
`confirmed-data-up` is shown as “confirmed data up”.

<Callout type="warning" emoji="🔐">
  Treat OTAA keys and ABP session keys as sensitive network credentials. The
  simulator displays them to support configuration, but they should not be
  shared in screenshots or public profile exports.
</Callout>

## Location

| Field | Meaning | Accepted value |
| --- | --- | --- |
| `latitude` | North/south position used by the map and simulation. | Decimal degrees from `-90` to `90`. |
| `longitude` | East/west position used by the map and simulation. | Decimal degrees from `-180` to `180`. |
| `altitude` | Height above sea level. | Numeric value in meters. The map can request an altitude for the selected coordinates. |
| `region` | LoRaWAN regional band plan. | `EU868`, `US915`, `CN779`, `EU433`, `AU915`, `CN470`, `AS923`, `KR920`, `IN865`, or `RU864`. |

The location fields are required. Selecting a point on the map updates the
coordinates used by the form.

## Activation credentials

Only the credential group matching the selected activation type is displayed.

### OTAA (`oota`)

| Field | Meaning | Accepted value |
| --- | --- | --- |
| `joinEUI` | Identifies the application entity that handles the join. | Required hexadecimal value with exactly 16 characters. |
| `appKey` | Secret key used to authenticate the OTAA join. | Required hexadecimal value with exactly 32 characters. |

### ABP (`abp`)

| Field | Meaning | Accepted value |
| --- | --- | --- |
| `devAddr` | 32-bit address assigned to the device. | Required hexadecimal value with exactly 8 characters. |
| `nwkSKey` | Network session key. | Required hexadecimal value with exactly 32 characters. |
| `appSKey` | Application session key. | Required hexadecimal value with exactly 32 characters. |

Changing activation mode after creation is intentionally disabled because it
changes the meaning of the session credentials.

<Tabs items={["OTAA", "ABP"]}>
  <Tabs.Tab>
    **OTAA** devices start without application session parameters. They must
    complete a join exchange before normal application uplinks can be
    delivered.
  </Tabs.Tab>
  <Tabs.Tab>
    **ABP** devices start with the session address and keys already configured.
    They do not need an OTAA join exchange before transmitting application
    traffic.
  </Tabs.Tab>
</Tabs>

## LoRaWAN and Raw LoRa

Choose **Radio Protocol** to control what the device transmits:

| Value | Behavior |
| --- | --- |
| **LoRaWAN** | Uses LoRaWAN frames and the configured OTAA or ABP session. OTAA devices must join before sending application data. |
| **Raw LoRa** | Sends the payload bytes directly, without a LoRaWAN header, encryption, MIC, or OTAA join. |

Choose **Radio Receive Mode** separately:

| Value | Behavior |
| --- | --- |
| **LoRaWAN** | Accepts LoRaWAN traffic through the normal session checks. |
| **Raw LoRa** | Accepts raw traffic without interpreting its bytes as LoRaWAN. |
| **Auto** | Recognizes structurally valid LoRaWAN frames and processes them as LoRaWAN; other payloads are treated as raw frames. |

For a raw-only scenario, select **Raw LoRa** in both fields. Use **Auto** when
the device should accept both protocols. The transmit protocol and receive
mode are independent; selecting one does not change the other.

The shared device form still requires its identity, activation credentials,
class, and other configuration groups. These credentials do not add LoRaWAN
security or a join exchange to raw transmissions. Configure the payload as text
or enable **Base64 Encoded** to supply exact binary bytes. Location, antenna
range, regional radio settings, collisions, and packet loss still affect raw
transmissions. An inactive device does not transmit or accept raw traffic.

<Callout type="info" emoji="📻">
  Raw LoRa does not provide LoRaWAN application ports, MAC commands, or
  confirmed-message acknowledgements. The payload codec described below
  decodes LoRaWAN application uplinks; raw bytes are shown as hexadecimal data
  in the event stream and logs.
</Callout>

## Receive windows

The RX1 and RX2 groups describe how the device listens for downlinks after an
uplink.

| Group | Field | Meaning | Constraint |
| --- | --- | --- | --- |
| RX1 | `delay` | Delay before opening RX1. | Integer, zero or greater, in milliseconds. |
| RX1 | `duration` | RX1 listening duration. | Integer, zero or greater, in milliseconds. |
| RX1 | `dataRateOffset` | Data-rate offset applied to RX1. | Integer, zero or greater. |
| RX2 | `delay` | Delay before opening RX2. | Integer, zero or greater, in milliseconds. |
| RX2 | `duration` | RX2 listening duration. | Integer, zero or greater, in milliseconds. |
| RX2 | `channelFrequency` | Frequency used by RX2. | Positive numeric value in hertz. |
| RX2 | `dataRate` | Data rate used by RX2. | Integer, zero or greater. |
| RX2 | `ACKTimeout` | Time allowed for an acknowledgement after a confirmed uplink. | Integer from `1000` to `3000` milliseconds. |

The form provides contextual information beside the receive-window fields. If
you are reproducing a network setup, keep the RX1 and RX2 values consistent
with the receive-window behavior expected by the device.

## Frame configuration

| Field | Meaning | Accepted value |
| --- | --- | --- |
| `fPort` | Application port used to identify the payload type. | Integer from `1` to `223`. |
| `retransmission` | Number of retries after a transmission failure. | Integer, zero or greater. |
| `FCntUp` | Uplink frame counter. | Optional; when supplied, zero or greater. |
| `FCntDown` | Downlink frame counter. | Optional; when supplied, zero or greater. |
| `disableFrameCounterValidation` | Disables frame-counter validation. | Toggle. Keep disabled unless the simulation scenario requires it. |

## Payload configuration

| Field | Meaning | Accepted value |
| --- | --- | --- |
| `uplinkInterval` | Time between consecutive uplinks. | Required positive value in seconds. |
| `oversizedPayloadBehavior` | What to do when a payload exceeds the allowed size. | `fragment` splits it into multiple transmissions; `truncate` cuts it to the maximum size. |
| `MType` | LoRaWAN uplink message type. | `confirmed-data-up` requests an acknowledgement; `unconfirmed-data-up` does not. |
| `payload` | Application data transmitted by the device. | Required text or encoded data. |
| `base64Encoded` | Whether `payload` is Base64 encoded. | Toggle. When enabled, the form validates Base64 input. |

### Payload codec

Enable **Payload Codec** when the application payload should also be shown as
structured data. Paste a JavaScript function named `decodeUplink` into the
multiline editor:

```js
function decodeUplink(input) {
  return {
    data: {
      temperature: input.bytes[0],
      humidity: input.bytes[1],
    },
  };
}
```

The function receives:

| Property | Meaning |
| --- | --- |
| `input.bytes` | The decrypted application payload as an array of byte values. |
| `input.fPort` | The application port configured for the uplink. |

Return an object with a `data` object containing the values you want to see in
the event stream. The simulator checks the JavaScript syntax and the presence
of `decodeUplink` when the device is saved. During a run, the function is
executed with a short time limit; a codec error is reported on the event and
does not stop the simulation.

When decoding succeeds, the event stream and the simulation log show the
result next to the original event as **Decoded** data. The codec is applied to
application uplinks only, after the LoRaWAN payload has been decrypted.

<Callout type="warning" emoji="⚠️">
  Treat codec scripts as configuration code. Keep them small, deterministic,
  and free of external dependencies. The simulator does not provide access to
  the application, the filesystem, or network services from a codec.
</Callout>

## Advanced configuration

| Field | Meaning | Accepted value |
| --- | --- | --- |
| `antennaRange` | Maximum communication distance used by the simulation and map. | Required positive value in meters. |
| `ADREnabled` | Allows the network to optimize data rate and transmission power. | Toggle. |

When a device is selected on the map, `antennaRange` is rendered as a white
dashed coverage circle around the marker. This is a visual indication of the
configured range, not a guarantee of successful radio delivery.
